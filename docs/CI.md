# Continuous integration and native build verification

The repository includes three GitHub Actions workflows:

- `.github/workflows/validate.yml` runs on pushes, pull requests and manual dispatch. It requires a committed `package-lock.json`, installs with `npm ci`, runs `npm run verify:all` and `npm run typecheck`, checks Expo SDK package compatibility, and resolves the public Expo config to verify the persistent app IDs and single-feed configuration.
- `.github/workflows/native-build.yml` runs on pushes to `main` and manual dispatch. It runs the source/type checks first, then generates and compiles an Android debug APK and/or an unsigned iOS Simulator app. A manual run can select Android, iOS or both. The resulting artifacts are retained for 14 days.
- `.github/workflows/bootstrap-lockfile.yml` is manually triggered while the repository still has no lockfile. It resolves the dependencies on a networked GitHub runner, validates the generated npm lockfile, proves a clean `npm ci` install, runs the source/type/Expo compatibility checks, and uploads `package-lock.json` plus its SHA-256 checksum for review. It does not write to the repository.

## First-time lockfile bootstrap

This source checkpoint deliberately does not contain a fabricated lockfile. The npm registry was not resolvable from the environment used to prepare it, so the full dependency graph and integrity hashes could not be generated honestly.

1. Add this source archive to the intended GitHub repository and push it.
2. Open **Actions → Bootstrap npm lockfile → Run workflow**.
3. Download the `sheademtula-package-lock-*` artifact from the completed run.
4. Review `package-lock.json`, verify its checksum, copy the lockfile to the repository root, and commit it.
5. Re-run validation. The normal source and native workflows intentionally stop with a clear error until this lockfile is committed.

A networked development machine can perform the same bootstrap locally:

```bash
npm install --package-lock-only --ignore-scripts --no-audit --no-fund
node scripts/check-lockfile.mjs
npm ci --no-audit --no-fund
npm run verify:all
npm run typecheck
npx expo install --check
```

The lockfile checker requires npm lockfile version 3 and verifies the root package identity plus the complete set and declared ranges of direct dependencies/devDependencies. It does not invent lock entries or pin transitive packages itself; the lockfile must be generated by npm and reviewed before commit.

## Native build behavior

The native workflow uses GitHub-hosted runners because the development container used for this checkpoint does not have the platform toolchains:

- Android: Ubuntu 24.04, Temurin JDK 17, Android SDK Platform 37 and Build Tools 37.0.0. `expo prebuild` generates the native project, and Gradle compiles `app-debug.apk`.
- iOS: the `xcode-27` macOS runner, matching SDK 58's iOS 27 baseline. `expo prebuild` generates the native project, CocoaPods resolves native dependencies, and Xcode compiles an unsigned generic iOS Simulator application.

Both builds compile local Expo modules, generated AppDelegate integration, config plugins and native application code. They do not sign app-store releases, install on physical devices, or verify runtime background behavior. A successful simulator compile is not a substitute for checking background audio, DownloadManager, background URLSession, notifications, audio effects, RTL and media interruption handling on hardware.

No Expo account, EAS project ID, Apple signing credentials, Google Play credentials or store submission secret is required by these CI workflows.

## Running checks locally

Once `package-lock.json` is committed:

```bash
bash scripts/ci-install-dependencies.sh
npm run verify:all
npm run typecheck
npx expo install --check
npx expo config --type public --json
```

Native build commands on a correctly configured machine:

```bash
npx expo prebuild --platform android --clean
cd android && ./gradlew --no-daemon :app:assembleDebug
```

```bash
npx expo prebuild --platform ios --clean
cd ios && pod install
xcodebuild -list -workspace ./*.xcworkspace
```

The CI workflow is the authoritative command sequence for the generated iOS workspace and simulator build.

## CI safety

Workflows have read-only repository permissions, do not check out untrusted pull requests with privileged triggers, do not receive signing or publishing secrets, and upload only the npm lockfile or unsigned debug/simulator build artifacts. The bootstrap workflow deliberately does not commit dependency changes automatically; a developer reviews and commits the generated lockfile. Protect `main` with the validation checks before accepting changes.
